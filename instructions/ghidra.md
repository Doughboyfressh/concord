# Machine specifications before machine guesses

For a request about how a binary is decoded — which architecture, which calling convention, which registers, where the entry points are — read the specification rather than inferring it. Ghidra's processor corpus is data and is read natively here: 189 languages across 59 processor families from `.ldefs`, each processor's registers and entry-point vectors from `.pspec`, each compiler's calling conventions from `.cspec`, the loader's architecture decision table from `.opinion`, and the compiled decode tables from `.sla`. These are `read` effects over bytes already in the workspace, so they need no approval and nothing is launched.

When the question is which language a binary should be decoded as, resolve it instead of guessing. `artifact.ghidraLanguageMatch` matches the header fields against the `.opinion` constraint rows and reports only languages that the `.ldefs` actually declares. A row that matched but names no installed language is reported as matched-and-unresolved, which is the honest answer; an assembled identifier like `processor:LE:32:variant` would look like a result for every row, including rows whose language is not present. Headerless firmware has no fields to match, so it has no resolvable language — say that rather than offering the most likely architecture as though it were read.

A specification describes how to decode a binary. It is not evidence about any particular binary, and these readers are marked untrusted for that reason. A calling convention says how the compiler was expected to pass arguments; it does not establish that a given function does. A default symbol table gives the architecture's reset and interrupt vectors; it does not establish that the artifact in hand uses them.

Distinguish the compiled form from the source. A `.sla` records what the SLEIGH compiler concluded for exactly one language variant, with the preprocessor already resolved, so its endianness, alignment, address spaces and register set are facts. A `.slaspec` is the input and often states nothing on its own: `define endian=$(ENDIAN)` is how the ARM family declares endianness, and one ARM source tree describes 22 languages. So `artifact.sleighSource` reports each declaration with the `@if` conditions guarding it and never resolves them. Treat a guarded declaration as conditional, and treat an unresolved macro as unresolved; attributing one variant's registers to all of them is the specific error this shape exists to prevent.

`artifact.compareSleighSource` has three outcomes rather than two. Agreement and disagreement mean what they say, and *unstated* means the source did not speak — a macro, a guard, or a fact declared in a file that was not followed. Do not report an unstated field as a mismatch; that manufactures a finding out of the preprocessor.

Disassembly is available and is native. `artifact.disassemble` decodes instructions from a compiled table and a byte range for any of the 189 shipped language variants, as a `read` effect needing no approval. Each line carries the constructors that matched, so a claim about an instruction can be traced to the SLEIGH that produced it. Two cautions apply. Supply the initial context: it is declared in the `.pspec` and read by `artifact.ghidraProcessorSpec`, and without it a context-dependent language decodes in whatever its zeroed context selects — x86 reports `PUSH BP` where the 32-bit language means `PUSH EBP`, which is correct for the bits it was given and wrong about the program. And decoding stops at the first position no constructor claims rather than resynchronising, so a short run of instructions followed by a stop means those bytes are not instructions in that language, not that the decode failed.

Pass `pcode: true` for what each instruction does rather than only what it is called. P-code is Ghidra's architecture-independent intermediate representation — an operation, an optional output varnode and its inputs, each naming an address space, an offset and a size — so a question about effects can be answered the same way on any of the 189 variants. Two distinctions in that output carry weight. An empty p-code list with an `UNIMPLEMENTED` directive is not an instruction that does nothing; it is an effect the table does not model, and reporting it as a no-op would be wrong. And a delay slot means the following instruction executes as part of this one, so the p-code shown is not the whole effect; the omission is stated rather than left to be inferred.

`artifact.controlFlow` goes one step further and recovers basic blocks, their edges and the call graph. Because it reads only the six flow operations, it behaves the same on every variant. Three of its rules are worth holding onto when reading its output: a call is a call edge and not a control-flow edge, so a block runs through a call rather than ending at it; an indirect branch is reported as unresolved rather than omitted, so treat it as a known gap and not as dead code; and reachability is followed from the entry points supplied, so an address absent from the result was either never reached or was reached only through an unresolved branch. Supply the entry points you mean, because the default is the start of the range.

`artifact.callGraph` follows calls across regions and returns every region reachable from the entry points, plus the graph between them. Read three things in its output carefully. A `tail` edge is marked `candidate`: flow certainly left one region and arrived at the entry of another, but whether that was a tail call or two functions placed adjacently is not decidable from the instruction, so do not report it as a call. An `external` node is a call target outside the analysed range — the edge is real, the body was not read. And an indirect call produces no node at all, which makes every call graph a lower bound: say what it resolved, never that those are all the calls.

`artifact.dataflow` answers which write supplies each read. Its summary names the storage a region reads before writing — its inputs — and the storage it writes, which is the evidence a calling convention is recovered from and can be compared with what the `.cspec` declares. Four things bound every answer it gives, and all four are stated in its own limitations. It computes reaching definitions, not SSA, so a read with several reaching definitions is a genuine join and not a defect. A definition kills a previous one only when it fully covers it, so a narrow write leaves a wider value alive and partially overwritten. Memory through a computed pointer is not resolved, so no load is attributed to any store and a slice ends where a value came out of memory. And the chains come back only with `detail: true`; without it the counts still describe the whole analysis.

What stays outside is decompilation, and not because it is unbuilt. Ghidra's analyzer and decompiler require a Java runtime, and `decompile.exe` is not a standalone tool — it is a slave process of the JVM host, reading a burst protocol on stdin and calling back for memory, symbols and specifications. Recovering C from an artifact therefore needs the reviewed provider under the `process` effect, with a pinned executable and an argv the operator wrote. When a request needs that, say it requires separately provisioned tooling and explicit authorization rather than presenting it as available. Decoding an instruction is not decompiling it: a mnemonic and its operands say what an instruction is called and what it addresses, not what the surrounding function computes.

Ghidra is Apache 2.0, and the `.sla` id tables here are transcribed from its source. Naming a processor, a language id, or a userop grants nothing: these are indexed descriptions of another program's data.
