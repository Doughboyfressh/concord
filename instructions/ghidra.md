# Machine specifications before machine guesses

For a request about how a binary is decoded — which architecture, which calling convention, which registers, where the entry points are — read the specification rather than inferring it. Ghidra's processor corpus is data and is read natively here: 189 languages across 59 processor families from `.ldefs`, each processor's registers and entry-point vectors from `.pspec`, each compiler's calling conventions from `.cspec`, the loader's architecture decision table from `.opinion`, and the compiled decode tables from `.sla`. These are `read` effects over bytes already in the workspace, so they need no approval and nothing is launched.

When the question is which language a binary should be decoded as, resolve it instead of guessing. `artifact.ghidraLanguageMatch` matches the header fields against the `.opinion` constraint rows and reports only languages that the `.ldefs` actually declares. A row that matched but names no installed language is reported as matched-and-unresolved, which is the honest answer; an assembled identifier like `processor:LE:32:variant` would look like a result for every row, including rows whose language is not present. Headerless firmware has no fields to match, so it has no resolvable language — say that rather than offering the most likely architecture as though it were read.

A specification describes how to decode a binary. It is not evidence about any particular binary, and these readers are marked untrusted for that reason. A calling convention says how the compiler was expected to pass arguments; it does not establish that a given function does. A default symbol table gives the architecture's reset and interrupt vectors; it does not establish that the artifact in hand uses them.

Distinguish the compiled form from the source. A `.sla` records what the SLEIGH compiler concluded for exactly one language variant, with the preprocessor already resolved, so its endianness, alignment, address spaces and register set are facts. A `.slaspec` is the input and often states nothing on its own: `define endian=$(ENDIAN)` is how the ARM family declares endianness, and one ARM source tree describes 22 languages. So `artifact.sleighSource` reports each declaration with the `@if` conditions guarding it and never resolves them. Treat a guarded declaration as conditional, and treat an unresolved macro as unresolved; attributing one variant's registers to all of them is the specific error this shape exists to prevent.

`artifact.compareSleighSource` has three outcomes rather than two. Agreement and disagreement mean what they say, and *unstated* means the source did not speak — a macro, a guard, or a fact declared in a file that was not followed. Do not report an unstated field as a mismatch; that manufactures a finding out of the preprocessor.

What stays outside is the engine, and not because it is unbuilt. Ghidra's analyzer and decompiler require a Java runtime, and `decompile.exe` is not a standalone tool — it is a slave process of the JVM host, reading a burst protocol on stdin and calling back for memory, symbols and specifications. Disassembling or decompiling an artifact therefore needs the reviewed provider under the `process` effect, with a pinned executable and an argv the operator wrote. When a request needs that, say it requires separately provisioned tooling and explicit authorization rather than presenting it as available. Reading a specification is not decompilation, and a mnemonic list taken from a constructor's display section says what an instruction is called, not what it does.

Ghidra is Apache 2.0, and the `.sla` id tables here are transcribed from its source. Naming a processor, a language id, or a userop grants nothing: these are indexed descriptions of another program's data.
