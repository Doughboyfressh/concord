## Where the training is still blind

Derived from the source and from the predictions themselves, not recorded by hand. Tool
coverage is saturated, so these are the axes that still discriminate.

**Refusal codes.** 199 distinct codes are thrown across `src/`. 179 are named by a prediction and 192 were actually raised during this round, leaving 13 whose reachability from a plan is unproven. A further 8 codes only ever appear as data in an object literal, mixing the engine's own failure codes with warnings a tool returns inside a successful answer; they are excluded from the count above because a warning cannot be reached by refusing anything. Of what remains, much is raised while building a registry or driving a browser, where no plan reaches it, so this is a frontier rather than a failing grade — but it is not all unreachable, and the list below is where to look.

**Output keys.** 635/635 declared output keys are read by some prediction. A key no prediction reads has never been checked against a real run.

**Composition.** 97 of the 97 registry tools an exercise names appear in a plan with more than one task; 0 are exercised only alone. A further 66 exercise labels are not plan-addressable at all - factories, engine entry points, value helpers, and tools a configured adapter would have to register - and are counted separately rather than held against this axis. The kernel exists to compose tools, so this is the axis where a high tool count is most misleading.
